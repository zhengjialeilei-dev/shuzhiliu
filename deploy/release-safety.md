# 发布与作品版本保护

## 本轮边界

- 发布前保留正在运行的 API 镜像，并为每次发布尝试创建独立备份目录。
- 先备份数据库、构建 API、执行向后兼容迁移，再启动 API 并检查健康状态。
- API 就绪后复制前端资源，最后通过同文件系统 rename 切换 index.html。
- 切换前执行 `deploy/check_release.mjs`，核对健康响应内容、分页和预览接口；切换后通过公网核对构建入口 SHA-256 与 JS/CSS。任何失败仍由发布错误处理流程尝试回滚。
- 不删除旧版 assets，避免已打开页面的懒加载脚本 404。
- 发布命令失败时尝试恢复旧入口与旧 API 镜像，仍以失败状态退出。
- 数据库不会自动回灌；迁移必须采用向后兼容的扩展方式。破坏性迁移需要独立维护窗口和恢复方案。
- 这是入口原子切换，不是整站蓝绿发布：API 重启仍可能有短暂中断，非哈希 public 文件目前仍原地复制，不承诺这些文件的整站事务回退。
- 进程被强制终止、主机断电或 TAT 超时不能依赖 ERR trap 完成恢复，需使用下面的恢复记录。

## 恢复记录

服务器原工作区 `deploy/backups/release-<commit>.<unique>/` 中包含：

- `database.dump`：本次迁移前的数据库备份；恢复须单独确认。
- `api-image-id` / `api-rollback.yml`：原 API 镜像及 Compose 覆盖配置。
- `web/index.html`：旧入口；`web/next-index.html`：本次新入口。

恢复网站入口：先在服务器明确选定上述本次备份目录，再 source `deploy/web_release.sh`，调用 `rollback_web_release <站点目录> <备份目录/web>`。该操作不清理新旧资源。

恢复 API：使用正常发布相同的 Compose 项目目录和环境文件，在基础 Compose 配置后追加该备份目录的 `api-rollback.yml`，执行 `up -d --no-build --pull never api`，随后检查本机及公网 `/api/health`。不得自动恢复数据库来掩盖迁移失败。

## 教学作品替换

- 新上传文件本身使用带唯一标识的地址；成功替换不再删除旧作品和旧封面。
- `20260916_preserve_resource_revisions.sql` 为资源更新增加事务内版本快照（`resource_revisions`），失败更新不会留下成功快照。
- 版本历史从迁移生效后开始，不会恢复此前已经删除的文件。
- 作品解析及 HTML 代理响应使用 `Cache-Control: no-store`；新播放器在解析后携带版本参数，避开此前缓存的无版本代理地址。
- 服务端仍保留有容量限制的 HTML 缓存，键包含真实资源版本，不使用用户随意指定的版本作为缓存键。
- 本轮没有提供后台“一键恢复作品”界面。版本快照和旧文件为后续恢复功能提供基础。
- 主动删除作品仍会删除当前作品文件；历史快照/旧文件保留，不等于彻底擦除。

## 保留与清理

本阶段不自动清理旧作品、旧脚本、发布备份和带标签的回退镜像。需关注磁盘/COS容量；后续清理必须先核对当前引用、历史引用、恢复窗口和仍可能使用的课堂页面。不要在发布步骤中按“本次构建未出现”直接删除。

## 验证

- `npm run test:release`：本地临时目录验证入口切换、旧资源保留、入口回退、真实发布错误处理函数和 shell 语法；Docker 调用使用替身，不操作服务器。
- `npm run test:revisions`：显式配置 `REVISION_TEST_DATABASE_URL` 后，建立随机测试 schema，验证真实 PostgreSQL 迁移、版本快照、失败更新回滚和重复执行。没有该变量会跳过，不读取生产 `.env`。
- GitHub Actions 已配置独立 PostgreSQL 测试服务，在部署之前执行迁移测试。
- 首次生产使用前仍需检查迁移、服务器磁盘、备份和旧镜像可用性，并在维护窗口验证真实容器恢复。
- 发布范围与待确认事项见 [本次发布候选清单](release-candidate.md)。只读检查覆盖健康、分页、预览身份和入口资源，不代替浏览器课堂验收。
